# 编排画布架构设计（Orchestration Canvas）

> 画布的最终目标：**编排**。以工作区为基底，把 agent 预设（agent 节点）、任务（任务节点）、
> 渠道（渠道节点）等各类节点放置其上，用关联关系表达编排意图。
> 画布视图插件**只负责**：定义节点模型、节点注册协议、编排关系的表达、展示、画布数据存储。
> **节点类型与连线规则都可以由其它插件扩展注册**。
>
> 本文是**概念层设计**；权威协议规格（类型定义、API 签名、交互管线、校验规则、版本兼容）
> 见 [protocol-spec.md](protocol-spec.md)（单一事实源）。
> 本文末尾（§9）是**设计决策记录**——关键取舍的结论与理由，改设计前先读。

---

## 1. 角色分工（谁做什么）

```text
┌─────────────────────────────────────────────────────────────┐
│ dsh-workspace-canvas（编排画布）                              │
│   定义并维护：                                               │
│   · 画布文档模型（nodes / edges / view）                     │
│   · 节点/连线规则注册协议（ctx.canvas 服务）                 │
│   · 画布操作（拖拽/缩放/平移/连线/对齐/布局/持久化）          │
│   · 展示框架（节点渲染、边渲染、面板）                       │
│   不执行任何业务：不跑 agent、不调度任务、不发送渠道消息      │
├─────────────────────────────────────────────────────────────┤
│ 节点插件（示例：dsh-agent-presets / dsh-task-board / dsh-ssh）│
│   经 ctx.canvas.registerNodeType() 贡献：                    │
│   · 节点类型（kind）+ 外观 + 实例数据读写 + 动作 + 边语义     │
│   业务数据留在自己的领域，画布只存「引用 + 布局 + 关系」      │
├─────────────────────────────────────────────────────────────┤
│ 连线规则插件（可与节点插件同源）                             │
│   经 ctx.canvas.registerEdgeRule() 贡献：                    │
│   · 边类型 + 连接合法性 + 数量约束 + 业务钩子 + 渲染          │
│   画布只提供连线协议（手势/存储/渲染框架），不实现具体连线业务 │
└─────────────────────────────────────────────────────────────┘
```

## 2. 画布文档模型（概念）

画布全部持久化状态收敛为**一个文档对象**（纯 JSON，可序列化、可迁移版本）：

```text
CanvasDocument v1
├── version: 1
├── view?  { x, y, zoom }        画布视图（「镜头」：平移 + 缩放，不影响坐标）
├── nodes: CanvasNode[]          节点（id / kind / ref / workspaceId? / label? / position / meta?）
│                                  · workspace 节点：全局坐标（px）；ref = 工作区 id
│                                  · 编排节点：所属工作区区域内坐标（px）；workspaceId 必填
└── edges: CanvasEdge[]          关系边（id / kind / source / target / meta?）—— 仅关联语义
```

**核心不变量：工作区 = 强制 scope 容器**

- **工作区是画布最基础的节点，其它节点不可脱离工作区而存在**；
- 一个完整画布 = 多个工作区；一个工作区 = 一个区域（scope 小画布），该区域的全部节点都隶属该工作区；
- 每个编排节点（`kind !== 'workspace'`）**必带 `workspaceId`**（业务工作区 id，与 workspace 节点 `ref` 同值）；
  缺失或非法 → `meta.invalid='no-scope'`，不渲染并提示；
- **归属是字段不是边**：不存在 member 边；edges 只表达节点间关联（link / 扩展边）；
- 编排节点的 `position` 是**区域内局部坐标（px）**，渲染绝对位置 = 工作区节点位置 + 局部坐标；
  拖工作区 = 成员整体跟随；缩放/平移只动「镜头」，不动坐标；
- 编排连线（`link`/扩展边）默认**仅限同工作区内**（按两端 `workspaceId` 相等判定），跨工作区连线
  需边规则显式声明 `crossScope`；
- **工作区节点 = 官方 feed 投影 + 位置存档**：文档存工作区节点（ref/position），实例数据实时读
  `ctx.workspaces`；feed 消失的工作区 → 提示 + 级联清理其成员；
- **删除工作区 = 级联删除其成员**（成员无独立存在），删除前确认提示。

**数据边界（关键约定）**：画布文档**不含业务数据**——不存 agent 配置、任务内容、渠道密钥；
只存「引用 + 布局 + 关系」。业务数据在各自插件域。因此：卸载画布插件只丢布局，不丢业务；
节点插件升级数据结构不影响画布文档。

> 完整类型定义、字段约束、不变量、JSON 语义见 [protocol-spec.md §2](protocol-spec.md#2-数据模型canvasdocument-v1)。

## 3. 注册协议（概念）

画布提供 cordis 服务 `ctx.canvas`（消费方 `ctx.get('canvas')` + `declare module` 可选依赖，
同 web-ui-settings 的 `webUiSettings` 先例——画布缺席时节点插件正常降级）：

```text
ctx.canvas
├── registerNodeType(NodeTypeDefinition)     节点类型：kind/label/data.list/render/detail/actions/edgeKinds
├── registerNodeActions(kind, actions)       向任意 kind 追加上下文菜单动作（含内置 'workspace'）
├── registerNodeDetailSection(kind, section) 向任意 kind 追加右侧明细区块
├── registerEdgeRule(EdgeRuleDefinition)     连线规则：kind/label/accepts/arity/onConnect/onDisconnect/
│                                            renderEdge/metaFields/ports/validate
├── readDocument() / subscribe(fn)           文档读 + 订阅
└── mutate(mutator)                          文档写（校验/查重/持久化/广播）
```

**画布与插件的能力划分**：

| 维度 | 画布（协议方） | 插件（实现方） |
| --- | --- | --- |
| 节点 | 放置/拖拽/选中/连线/布局/持久化/归属校验 | 类型、实例数据读写、外观、动作、参与哪些边 |
| 连线 | 拖线手势、连接点、可连目标过滤/拒绝提示、边文档存储、默认渲染 | 能否连（accepts）、连几条（arity）、连上做什么（onConnect）、长什么样（renderEdge）、带什么数据（metaFields）、存量校验（validate） |
| 业务 | **零执行** | 全部业务（动作、钩子） |

> 完整接口签名与类型定义见 [protocol-spec.md §3](protocol-spec.md#3-ctxcanvas-服务契约)。

## 4. 关联关系模型（概念）

| 边类型 | 归属 | 语义 |
| --- | --- | --- |
| `link` | 画布内置（基础设施规则） | **自由关联**：同工作区内任意两节点，语义由端点节点插件解释 |
| `<scope>:<edge-kind>` | 插件注册 | 业务编排语义：任务依赖、渠道分发、agent 指派等，规则插件定义全部行为 |

**归属（scope）不是边**：编排节点的 `workspaceId` 字段即归属（§2）；`member` 概念已被字段取代。

**组合判定**：节点 `edgeKinds`（声明式：愿参与哪些边）∩ 边规则 `accepts`（命令式：具体能否连，
可看实例状态）= 可连目标集合；**且非 `crossScope` 边仅限同工作区内**（按 `workspaceId` 相等判定）。

**关系约定**：
- 删除节点 → 连带删除其全部边（先跑各边 `onDisconnect`）；
- **删除工作区（scope）→ 级联删除其全部成员节点与边**（成员不可脱离 scope），删除前确认提示
  （列出成员数）；工作区本身走官方 `ctx.workspaces.delete`（只删注册，目录与日志不动）；
- 规则插件卸载 → 该类边显示「未知规则」占位（数据保留），重装即恢复；
- 边不做自动布局推挤之外的空间约束（区域内自由，关系由边表达）。

> 交互管线（建边/删边/归属/校验规范）见 [protocol-spec.md §4](protocol-spec.md#4-交互管线规范)。

## 5. 存储契约

| 版本 | 存储 | 内容 | 说明 |
| --- | --- | --- | --- |
| v1（当前目标） | `localStorage['dsh.workspaceCanvas.doc.v1']` | 整个 `CanvasDocument` | 500ms 防抖写；版本字段就绪，未来可迁移 |
| v2（演进，可选） | 宿主 JSON 文件（经 `/api/dsh-workspace-canvas/doc` 路由，`dsh-storage-json` 或自定义） | 同上 | 文档较大/需跨浏览器共享时启用；**不占用官方 settings 命名空间**（settings 是配置域，不是文档存储） |

迁移与降级约定见 [protocol-spec.md §6-7](protocol-spec.md#6-版本与兼容)。

## 6. 节点与连线规则扩展约定（第三方插件接入）

1. **命名**：节点 kind `scope:type`、边 kind `scope:edge`，避免全局冲突；
2. **数据**：实例数据、增删改查全在插件域（官方 API 或插件自己的路由/服务）；画布只存 `ref`；
3. **归属**：节点由插件创建时必须带 `workspaceId`（或经拖入工作区区域由画布写入），画布校验归属完整；
4. **生命周期**：插件 `apply` 时注册、卸载时注销（注册 API 返回 disposer）；
5. **卸载兼容**：节点插件卸载后画布显示「未知类型」占位（保留位置与边），重装即恢复；画布**不删除**插件数据；
6. **动作/钩子**：节点业务动作与连线业务钩子由插件实现，画布只做菜单与触发转发；
7. **校验**：`mutate` 时画布校验 kind 已注册、ref 引用合法、workspaceId 完整、边完整性；
   无效项标记 `meta.invalid=true` 而非静默丢弃；
8. **连线规则**：业务连线（任务依赖、渠道分发、agent 编排等）一律经 `registerEdgeRule` 注册，
   画布只提供协议。

## 7. 与 hundun-web 的关系

- 借用的机制：scene 坐标 + view 变换、单一拖拽状态机、四边连接点 + 方向滞回、吸附/对齐/碰撞推挤、
  GRID 自动布局、localStorage + 防抖持久化、**簇核/成员模型**（工作区 = 簇核、成员 = 区域内相对坐标，
  拖工作区整体跟随——与「工作区 = scope 容器」一致）；
- 差异：hundun-web 是**单体应用**（节点类型写死在 App.tsx）；本画布是**平台**（节点类型与连线规则
  均经注册协议扩展）；且在「成员必须贴簇核」的基础上放开为——成员必须在工作区区域内（scope 强制），
  区域内可自由排布（相对坐标），编排连线（link/扩展边）默认限同工作区内，跨工作区连线需显式声明；
  归属用节点 `workspaceId` 字段表达（hundun-web 的 member 概念在本设计中是字段而非边）。

## 8. 边界重申（详见 capability-boundaries.md）

- 画布 = **编排意图的表达、存储、展示、触发转发**；不执行任何业务；
- 业务执行者 = 节点插件（agent 预设插件跑 agent、task-board 跑任务、渠道插件发消息）；
- 数据 = 画布文档（引用+布局+关系）与业务数据严格分离；
- 扩展 = 一切新节点类型经 `ctx.canvas.registerNodeType` 进入，一切业务连线规则经
  `ctx.canvas.registerEdgeRule` 进入，画布不做硬编码类型、不实现具体连线业务。

## 9. 设计决策记录

> 本文档定稿阶段的关键取舍。每条含：结论、理由、替代方案。改设计前先读这里。

| # | 决策 | 结论 | 理由 | 替代方案（否决理由） |
| --- | --- | --- | --- | --- |
| D1 | 坐标模型 | **场景绝对像素 + 视图变换**：`position` 是 px 坐标，`view {x,y,zoom}` 是「镜头」，缩放平移不改坐标 | 「东西在哪」与「怎么看」分离是画布地基；区域尺寸变化、缩放下位置不漂移 | 百分比坐标（缩放/区域变化时漂移，返工）；像素+百分比混用（两套换算） |
| D2 | 归属模型 | **节点 `workspaceId` 字段，不是 member 边**：归属是文档约束，edges 只表达关联 | 归属是简单关系，建模成边会让查重/删边/拖线全系统特判；字段校验 O(1) 直观 | member 边（概念对称但复杂度泄漏到所有边操作） |
| D3 | 工作区节点持久化 | **文档存储工作区节点（ref + position），实例数据实时投影官方 feed**；feed 消失 → 提示 + 级联清理 | 拖动工作区位置刷新不丢；画布不缓存业务数据 | 纯投影（位置存不住，P0 的拖拽就白做） |
| D4 | 面板互斥协议 | **单一激活标记 + 共享常量包**：页面上一个 `data-dsh-panel-active="<name>"` 属性，后写者胜；协议常量/工具放聚合仓库共享包 `@hundun/dsh-panel-protocol` | 画布只需看「标记是不是我」，不需要认识所有面板；常量一处维护，新面板零改动 | 现状多属性硬编码（要枚举所有面板，改名即失效） |
| D5 | 配置语义 | **统一 `enabled` 总开关（双半区都生效）+ 独立 `announceToAgent`（仅控制 AI 公告）** | 一个开关管一半是语义分裂；公告与 UI 是两件事分开控制 | 现状 enabled 只管公告（界面按钮照常出现） |
| D6 | 规格与实现对齐 | **文档带「落地状态」标记（已实现 / 设计定稿 / 待实现）**，先定稿后实现 | 文档永远诚实，实现阶段每完成一块翻标记，杜绝「文档吹牛、代码打脸」 | 规格自称权威但超前实现（漂移风险） |
| D7 | 测试 | **控制器状态机 / 互斥协议 / 校验引擎必须有自动化测试**，P0.5 起补 | 平台承诺（校验/降级）没有测试 = 没地基 | 纯人工验证（改动越多越怕） |
| D8 | 右键动作扩展 | **`registerNodeActions(kind, actions)`**：第三方可向任意 kind（含内置工作区）追加/调整菜单动作，画布合并渲染 | 工作区删除等操作不止画布自己要用；「操作开放给其他插件」是编排平台的基本面 | 只有类型所有者能定义动作（扩展需改画布代码，不开放） |
| D9 | 明细面板扩展 | **`NodeTypeDefinition.detail` + `registerNodeDetailSection(kind, section)`**：类型所有者提供明细视图，第三方追加区块，按 order 合并渲染；画布提供工作区明细（基础信息 + 会话列表） | 点击节点看详情是核心交互；明细内容必须让其他插件能贡献（如 SSH 给工作区加主机状态） | 明细写死在工作区节点（其他插件无法扩展） |
| D10 | 设置页归属 | **「hundun-dsh」设置页由聚合包 dsh-all 提供骨架**（`settings.section` + 子槽位），各插件注册自己的栏目；画布第一个栏目 = 启用画布开关（`enabled`，双半区生效，无设置服务时组合配置兜底） | 聚合品牌设置面归聚合包，栏目按插件扩展，避免画布包揽所有设置；开关语义落实 D5 | 由画布插件自己注册整页（未来其他插件加栏目要改画布代码） |
